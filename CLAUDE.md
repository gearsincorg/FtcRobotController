# BIOBUZZ FTC Robot Controller

Fork of the FIRST `FtcRobotController` SDK (`origin` = gearsincorg/FtcRobotController, `upstream` = FIRST-Tech-Challenge). Team code lives in `TeamCode/`; `FtcRobotController/` is the stock SDK module and should not be edited. Working branch: `BIOBUZZ-Master`.

## Stack
- **Pedro Pathing 3.0** for driving/localization. Hardware config is in `pedro/Constants.java` (`Constants.create(hardwareMap)` returns the `Follower`; `create(hardwareMap, maxPathSpeed)` caps path speed in in/s via Foresight's `maxVelocityConstraint`, used by auto via `AUTO_MAX_SPEED`; Foresight's own `maxPathSpeed` is a 0-1 fraction of top speed, not in/s): mecanum drive, OctoQuad localizer, Foresight. Every `ForesightConfig` field (meaning, units, defaults, our values) is described in `pedro/ForesightConfig.md`. Tuners are in `pedro/procedures/` and `pedro/Tuning.java`.
- **SolversLib** command framework for opmodes, subsystems and button bindings (WPILib style). Replaced Ivy.
- Opmodes extend `CommandOpMode`; subsystems extend `SubsystemBase` and expose `...Command()` methods.

## Two chassis (prototype and production)
- The drive geometry differs, so `Constants` has a localizer + Foresight set per chassis; motor and pod directions are per chassis (gearing differs); motor names and OctoQuad ports are shared.
- The chassis is picked at runtime from the active robot configuration name: `res/xml/prototype.xml` or `res/xml/production.xml` (deployed with the app; select it on the Driver Station). Any other name throws at init. `Constants.chassis()` returns it; teleop shows it in telemetry.
- Keep the two XML configs in step when wiring changes. Tuners use the detected chassis, so paste tuning results into that chassis's block. Use `Constants.chassis()` for any other per-robot differences, but keep shared code shared.

## Layout (`TeamCode/src/main/java/org/firstinspires/ftc/teamcode`)
- `GFORCE_Auto`, `GFORCE_Teleop`: competition opmodes (group "Competition"). Teleop is field-centric with heading lock; buttons are bound in `bindButtons()`.
- `Subsystems/`: one class per mechanism:
  - `IntakeSubsystem`: collect and transfer. Intake motor (`intake`), transfer motor (`transfer`, moves the whole column), gate servo (`gate`), four digital ball sensors (active-low), one per ball position: `slot1` nearest the intake to `slot4` at the gate. The ball count is the number of sensors that see a ball (debounced `COUNT_DEBOUNCE_MS`): all four = full, none = empty. Nothing is inferred from a ball passing a sensor. Five modes, picked every loop by priority (intake / transfer / gate): SHOOTING (shoot held and the shooter is up to speed: INTAKE / FEED / open), SPINUP (shoot held, shooter not up to speed, including after a shot slows it: both stopped), CLEAR_ALL (clear held: REJECT / EJECT), EJECTING (eject held: REJECT / HOLD), FULL (four balls: intake HOLD / transfer PACKED), INTAKING (otherwise: INTAKE / TRANSFER until packed, then PACKED: packed = balls stacked from slot4 down with no gaps, `isPacked()`, so the transfer doesn't stall against the gate; a new ball at slot1 makes a gap and starts it again). Every power is prefixed by its motor: `INTAKE_POWER`, `INTAKE_HOLD_POWER`, `INTAKE_REJECT_POWER`, `INTAKE_EJECT_POWER`, `TRANSFER_POWER`, `TRANSFER_PACKED_POWER`, `TRANSFER_HOLD_POWER`, `TRANSFER_EJECT_POWER`; the slot pattern (not just the count) is debounced by `COUNT_DEBOUNCE_MS`. The gate has three positions: `GATE_INIT` during init only (teleop and auto, until START), `GATE_OPEN` in SHOOTING, `GATE_CLOSED` otherwise. While shoot is held (SPINUP or SHOOTING), clear and eject are ignored. Intaking is always on (from the first loop after START), so there's no intake button. Auto uses `shootAllCommand()` (ends when the count has read empty for `SHOT_CLEAR_MS`, or `VOLLEY_TIMEOUT_MS` after feeding first starts) and `intakeUntilFullCommand()` (just waits for full); teleop uses `shootWhileHeldCommand()`, `ejectCommand()`, `clearAllCommand()`. These commands don't require the subsystem, so they can be held together. No manual mode. Takes a `BooleanSupplier` for shooter-ready. The intake and transfer motors must be in the config, unless `SIMULATED = true` (for now: no intake fitted), which uses no intake hardware at all and takes the balls from `SimulatedSlots`. The gate isn't fitted yet, so it's optional (skipped if missing). `SIMULATE_SENSORS = true` takes the sensors from `SimulatedSlots` (a ball count 0-4 packed against the gate, lighting slot4, slot3, ...: intake adds, feeding through the open gate shoots, full reverse ejects); it's false now (real sensors); telemetry warns while it's on.
  - `RobotCommands` (teamcode root): multi-subsystem commands for teleop and auto: `bindAutoAim` (track when full, idle when empty), `shootAll` (volley), `shootWhileHeld`.
  - Teleop controls: the intake collects by itself; hold LB chase the nearest yellow ball (robot-forward at `BALL_DRIVE_POWER` and turn toward it; pushing the left stick drives field-centric instead, twisting the right stick overrides the turn), hold RB shoot (also turns point-at-goal on; no ball is fed until `shooter.isReady()`: spun up and, because teleop calls `setRequireChassisAim(true)`, the chassis within `AIM_TOLERANCE_RAD` (10 deg) of the goal; then it feeds until released), hold B eject (intake out, transfer holds), hold Y clear all (intake and transfer reversed); the shooter tracks the goal the whole time from START (`shooter.track()` in `initialize()`: flywheel always at the table RPM and hood at the table angle for the current distance; never idled); Right Stick press toggles point-at-goal (the chassis turns to aim the shooter; on by itself when full, off by itself once empty with RB released; twisting the right stick overrides); telemetry shows the shooter idle / spinning up / aiming / READY; D-pad turns to a Pedro heading (up 90, left 180, down 270, right 0) and holds it until the stick is twisted (cancels point-at-goal); Share/Options select blue/red alliance; rumble on full / empty; gamepad LED shows count. Gamepad 2 D-pad up/down adds/removes simulated balls. `Util/IntakeTestOpMode` runs the intake state machine alone (A shoot, B eject, Y clear all, RB = "shooter ready").
  - `VisionSubsystem`: webcam AprilTag cluster tracking. Also a yellow ball finder on the same camera, always on: one `ColorBlobLocatorProcessor` over the whole image using `BiobuzzRobot.POLLEN_YELLOW` (the only ball color; no PredominantColorProcessor). Never disable the locator with `setProcessorEnabled(false)`: the SDK then draws the preview with no results and crashes (NPE in `ColorBlobLocatorProcessorImpl.onDrawFrame`). `getBlobs()` returns the SDK's own list, so copy it before filtering. Settings match the `Concept: Color-Locator (Rectangle)` test program: camera 320x240 with auto exposure (`MANUAL_EXPOSURE = false`; this also applies to AprilTags, which lose range), erode 3, blur 5, default box-fit drawing, blobs between `MIN_BALL_AREA` 400 and `MAX_BALL_AREA` 6000 pixels. It picks the blob lowest in the image (largest box-fit center y = nearest); `hasBall()`, `getBallError()` -1..+1 across the image, `getBallTurn()` (turn power from `BALL_TURN_GAIN`/`MAX_BALL_TURN`, 0 if no ball), `BALL_DRIVE_POWER` (0.2) for chasing. `Util/ColorTrackingTestOpMode` drives robot-centric and chases the ball while LB is held (sticks override); telemetry shows where it is (LEFT/CENTER/RIGHT, pixel x/y, error, area), LED yellow while seen.
  - `GimbalSubsystem`: two-servo gimbal (`pitch`, `roll`), positions -1..+1; `Util/GimbalOpMode` follows the right stick.
  - `ShooterSubsystem`: turret (motor + encoder), hood (servo) and one flywheel. It aims at the hive-Cell from Pedro odometry and leads the target to shoot on the move. Speed and hood come from `SHOT_TABLE` (distance → rpm, hood angle, flight time). Hood angle is degrees from vertical, forward positive; `hoodAngleToServo` is the only place that converts it to a servo position, using two measured points (`HOOD_ANGLE_A/B_DEG`, `HOOD_SERVO_A/B`; currently servo 0.64 = 0° (assumed), 0.96 = 25°) and limits the hood to that range. The table is a placeholder until measured with `Util/ShooterCalibrationOpMode` ("Shooter Calibration"): pick a point (D-pad: distance from the goal 12-96 in in 3 in steps (`MIN_DIST`, `MAX_DIST`, `DIST_STEP`), angle off the goal's front -60..+60 deg in 15 deg steps (`MAX_ANGLE`, `ANGLE_STEP`); `AUDIENCE/FAR_GOAL_FACING_DEG` are placeholders), X drives there with Pedro (sticks cancel) and turns aiming on when it arrives; aiming at the goal starts off, Right Stick press toggles it (twisting the right stick overrides); B flywheel on/off, Y/A RPM +/-100, RT/LT hood +/-1 deg, hold RB shoot, LB when a ball goes in (flight time: from the ball count dropping while SHOOTING, minus `COUNT_DEBOUNCE_MS`, to the press), Share saves the point to `/sdcard/FIRST/shooter_cal.csv` on the hub (one row per point: saving again replaces it), Options twice within 2 s deletes the selected point's row; every change first copies the file to `shooter_cal.csv.bak`; telemetry shows what's saved at the selected point. Bad data can also be removed on the PC: edit `tools/shooter_cal.csv` and `python tools/shotcal.py --push` (copies it back to the hub, the hub's old file to `.bak`), otherwise the next pull brings the lines back. Then `python tools/shotcal.py` (`--csv FILE`, `--dry-run`) pulls the CSV over ADB into `tools/shooter_cal.csv` (commit it), keeps the latest save per (goal, distance, angle), averages the angles at each distance into one row (untimed flight times from a line fit), shows the spread across angles, and rewrites `SHOT_TABLE` between the `// BEGIN/END GENERATED SHOT_TABLE` markers (don't hand-edit inside them). `setRequireChassisAim(true)` (teleop only; auto leaves it off because its paths don't face the goal) adds `isAimed()` (chassis within `AIM_TOLERANCE_RAD`) to `isReady()` while tracking, whatever `TURRET_ENABLED` says; `isAtSpeed()` is the flywheel part. `getGoal()` is the goal being aimed at (always the one on the robot's side); `getMeasuredRPM()` is the real flywheel speed (`getActualRPM()` returns the target while `TURRET_SIMULATED`). The flywheel is a goBILDA 5203 1:1 (28 ticks/rev, 6000 rpm); `setVelocity` takes ticks/s, so convert with `rpmToTicksPerSec()`. `Util/FlywheelTestOpMode` measures free speed, suggested PIDF and step response. The turret must be centered at init. `TURRET_ENABLED = false` for now: the turret is held at 0 and the chassis aims instead (`getAimError()`), and `isReady()` checks the robot heading. Each alliance has two goals, in Pedro coordinates: red audience (60, 54.5), red far (84, 54.5), blue audience (60, 89.5), blue far (84, 89.5) (blue is red with y flipped about 72). The shooter aims at the nearer goal of the selected alliance. (The published FTC-frame table didn't map cleanly onto Pedro, so don't convert from it.) `SIMULATED = true` (for now: no shooter fitted) uses no shooter hardware: the flywheel speed follows the target with a `SIM_SPINUP_S` time constant and telemetry warns. `FULL_SPEED = true` (temporary) runs the flywheel at full power instead of the table RPM and counts it ready `SPINUP_MS` after starting. Intake and transfer are in `IntakeSubsystem`.
- `Util/AutoConfig`: the auto setup menu shown during `GFORCE_Auto` init (gamepad 1 D-pad: up/down item, left/right change). Settings: alliance (goal side only; paths are not mirrored), start delay 0-15 s, path (one entry per `.turt` group, from the generated `paths/AutoRoutine`), cycles 0-2, park (None/Base), step mode (Off/On). Step mode is for testing: `robot.stepCommand(label)` (in `BiobuzzRobot`) pauses until gamepad 1 A is pressed (a fresh press), and finishes at once when step mode is off; every `autoCommand()` puts one after each path. Step mode is never saved, so it's off every time the opmode starts. The other settings are saved to `GFORCE_auto.properties` on the hub; teleop starts on the saved alliance. `GFORCE_Auto` schedules the chosen group's `autoCommand()` on the first loop after START. To add an auto: draw a `.turt` group and build; it shows up in the menu by itself.
- `Util/`: helper classes (`ClusterTracking`, `ClusterDisplay`) and test opmodes (`BasicOpMode_shaneshot`).
- `paths/Path_<Group>.java`: generated autonomous paths (see below).

## Autonomous paths: `.turt` -> Java
- Draw paths in Turtle Tracer and save the `.turt` files in `/turt_files`. Commit every `.turt` file.
- Files are grouped by the text before the last underscore (`NearCenter_start.turt`, `NearCenter_2.turt` -> group `NearCenter`). Each group needs exactly one `_start` file; its start position becomes `getStartPose()`.
- `tools/turt2java.py` writes `paths/Path_<Group>.java` for each group: `path_start()`, then `path_<suffix>()` for the rest in natural order (2, 3, ... 10), each returning a `FollowPathCommand`. A new file is copied from the template `paths/Path_GroupName.java` (its `autoCommand()` runs every path in order). After that, everything above the "Do not change anything above this line" banner is yours to edit (e.g. `autoCommand()`); everything below is regenerated on every run. It also regenerates `paths/AutoRoutine.java` (enum with one entry per group; do not edit).
- A line with a speed cap in Turtle Tracer (`maxSpeed` / `chainMaxSpeed` in the `.turt`, in/s; lowest wins) gets `.with(maxVelocity(n))`, a generated helper returning the follower's own `Foresight.config.maxVelocityConstraint.at(n)` (not `Constants.foresightConfig()`, which is a fresh copy). The cap applies only while that line runs.
- A bad group (e.g. no `_start` file) or `.turt` file prints an error and leaves every path file untouched.
- Run it manually with `python tools/turt2java.py`. The Gradle task `:TeamCode:generatePaths` does the same before every build (hooked to `preBuild`); a bad group fails the build. If Python isn't installed, the task warns and skips.
- `GFORCE_Auto` schedules `autoCommand()` on the first loop after START.

## Building
Build and deploy from Android Studio. The default shell Java may be 8, which is too old for the Gradle wrapper (needs 17+); use Android Studio's bundled JDK if building from a command line.

## Deploying to the robot (Wi-Fi ADB)
- The Gradle task `:TeamCode:adbConnect` (hooked to `preBuild`, so it runs on every build/Run) does `adb connect 192.168.43.1:5555` when the Control Hub is reachable. It never fails the build and skips quietly if you're not on the hub's Wi-Fi. `adb` is found via `sdk.dir` in `local.properties` or `ANDROID_HOME`.

## Conventions
- Keep opmodes thin; put mechanism logic in subsystems with command factories.
- Hardware names used so far: `front_left_drive`, `front_right_drive`, `back_left_drive`, `back_right_drive`, `octoquad`, `intake`, `transfer`, `gate`, `slot1`, `slot2`, `slot3`, `slot4`, `turret`, `shooter`, `hood`, `pitch`, `roll`, `Webcam 1`.

## Setting up a new PC
If the user says they are on a new machine, offer to run through this checklist (check each item with a command, don't assume):
1. `git clone` the repo and check out `BIOBUZZ-Master`. Confirm `git config user.name` / `user.email` are set.
2. Android Studio installed, with its bundled JDK (17+). Command-line `java -version` may still say 8; that's OK for Android Studio builds.
3. Python 3 on the PATH (`python --version`). Needed by the `generatePaths` Gradle task; without it `AutoPaths.java` can silently go stale. Verify with `python tools/turt2java.py` (should list every `turt_files/*.turt` file and leave `git status` clean).
4. Do a build in Android Studio and confirm it succeeds and `git status` stays clean.
5. Claude conversation history and memory are local to the old PC and are not in the repo; this file is the continuity.

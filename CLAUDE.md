# BIOBUZZ FTC Robot Controller

Fork of the FIRST `FtcRobotController` SDK (`origin` = gearsincorg/FtcRobotController, `upstream` = FIRST-Tech-Challenge). Team code lives in `TeamCode/`; `FtcRobotController/` is the stock SDK module and should not be edited. Working branch: `BIOBUZZ-Master`.

## Stack
- **Pedro Pathing 3.0** for driving/localization. Hardware config is in `pedro/Constants.java` (`Constants.create(hardwareMap)` returns the `Follower`; `create(hardwareMap, maxPathSpeed)` caps path speed in in/s via Foresight's `maxVelocityConstraint`, used by auto via `AUTO_MAX_SPEED`; Foresight's own `maxPathSpeed` is a 0-1 fraction of top speed, not in/s): mecanum drive, OctoQuad localizer, Foresight. Every `ForesightConfig` field (meaning, units, defaults, our values) is described in `pedro/ForesightConfig.md`. Tuners are in `pedro/procedures/` and `pedro/Tuning.java`.
- **SolversLib** command framework for opmodes, subsystems and button bindings (WPILib style). Replaced Ivy.
- Opmodes extend `CommandOpMode`; subsystems extend `SubsystemBase` and expose `...Command()` methods.

## Two chassis (prototype and production)
- The drive geometry differs, so `Constants` has a localizer + Foresight set per chassis; motor and pod directions are per chassis (gearing differs); motor names and OctoQuad ports are shared.
- The chassis is picked at runtime from the active robot configuration name: `res/xml/prototype.xml` or `res/xml/production.xml` (deployed with the app; select it on the Driver Station). Any other name throws at init. `Constants.chassis()` returns it.
- Keep the two XML configs in step when wiring changes. Tuners use the detected chassis, so paste tuning results into that chassis's block. Use `Constants.chassis()` for any other per-robot differences, but keep shared code shared.

## Layout (`TeamCode/src/main/java/org/firstinspires/ftc/teamcode`)
- `GFORCE_Auto`, `GFORCE_Teleop`: competition opmodes (group "Competition"). Teleop is field-centric with heading lock; buttons are bound in `bindButtons()`.
- `Subsystems/`: one class per mechanism:
  - `IntakeSubsystem`: collect and transfer. Intake motor (`intake`), transfer motor (`transfer`, moves the whole column), gate servo (`gate`), Flower Intake servo (`flower`, port 4 on both configs: `FLOWER_UP` 0.02, `FLOWER_DOWN` 0.45, `FLOWER_BUMPER` 0.40 (set on the robot 2026-11-26: the arm as a deflector so nectars don't catch on the front while driving in auto); positions are the `FlowerPosition` enum (`setFlower()`, `getFlower()`); UP from init in every opmode that uses the intake; `toggleFlower()` / `toggleFlowerCommand()` flip it (teleop L1: DOWN goes UP, UP or BUMPER goes DOWN), `flowerUpCommand()` / `flowerDownCommand()` / `flowerBumpCommand()` for auto (each ends `FLOWER_MOVE_MS` (200 ms) after setting the servo, so it has time to move); the Balls telemetry line ends with `flwr UP` / `flwr DN` / `flwr BMP`), four digital ball sensors (active-low), one per ball position: `slot1` nearest the intake to `slot4` at the gate. The ball count is the number of sensors that see a ball (debounced `COUNT_DEBOUNCE_MS`): all four = full, none = empty. Nothing is inferred from a ball passing a sensor. Five modes, picked every loop by priority (intake / transfer / gate): SHOOTING (shoot held and the shooter is up to speed: INTAKE / FEED / open; each time the gate opens (entering SHOOTING, including after a SPINUP dip) intake and transfer stay stopped for `GATE_OPEN_LEAD_MS` (150) so the servo is clear before a ball is pushed into it; the transfer runs at `TRANSFER_LAST_POWER` (1.0) instead of `TRANSFER_POWER` while one ball is left and for `TRANSFER_LAST_HOLD_MS` (250) after the count reads empty, so the last ball is pushed fully out), SPINUP (shoot held, shooter not up to speed, including after a shot slows it: both stopped), PASS (pass held: REJECT / EJECT, every ball out the intake), EJECTING (eject held: REJECT / HOLD), FULL (four balls: intake HOLD / transfer PACKED), INTAKING (otherwise: INTAKE / TRANSFER_EMPTY (0.2, slow) while empty, TRANSFER until packed, then PACKED: packed = balls stacked from slot4 down with no gaps, `isPacked()`, so the transfer doesn't stall against the gate; a new ball at slot1 makes a gap and starts it again). Every power is prefixed by its motor: `INTAKE_POWER`, `INTAKE_HOLD_POWER`, `INTAKE_REJECT_POWER`, `INTAKE_EJECT_POWER`, `TRANSFER_POWER`, `TRANSFER_EMPTY_POWER`, `TRANSFER_PACKED_POWER`, `TRANSFER_HOLD_POWER`, `TRANSFER_EJECT_POWER`; the slot pattern (not just the count) is debounced by `COUNT_DEBOUNCE_MS`. The gate has two positions: `GATE_OPEN` in SHOOTING, `GATE_CLOSED` otherwise, including during init (teleop and auto, until START). While shoot is held (SPINUP or SHOOTING), pass and eject are ignored. Intaking is always on (from the first loop after START), so there's no intake button. Auto uses `shootAllCommand(minShootTimeMs)` (through `BiobuzzRobot.aimAndShootCommand(minShootTimeMs)`, which aims the chassis first; both default to 0) (ends when the count has read empty for `SHOT_CLEAR_MS`, or `VOLLEY_TIMEOUT_MS` after feeding first starts, but never before `minShootTimeMs` has passed since feeding first started, so pollen released from the flower has time to reach the transfer; `aimAndShootCommand`'s overall limit is then the larger of `VOLLEY_MAX_MS` and `minShootTimeMs`) and `intakeUntilFullCommand(timeoutMs)` (just waits for full, or gives up after `timeoutMs`; 0 = no timeout); teleop uses `shootWhileHeldCommand()`, `ejectCommand()`, `passCommand()`. These commands don't require the subsystem, so they can be held together. No manual mode. Takes a `BooleanSupplier` for shooter-ready. The intake and transfer motors must be in the config, unless `SIMULATED = true` (currently false), which uses no intake hardware at all and takes the balls from `SimulatedSlots`. The gate isn't fitted yet, so it's optional (skipped if missing). `SIMULATE_SENSORS = true` takes the sensors from `SimulatedSlots` (a ball count 0-4 packed against the gate, lighting slot4, slot3, ...: intake adds, feeding through the open gate shoots, full reverse ejects); it's false now (real sensors); telemetry warns while it's on.
  - `Commands/RobotCommands`: multi-subsystem commands for teleop and auto: `bindAutoAim` (track when full, idle when empty), `shootAll` (volley), `shootWhileHeld`.
  - `Commands/JiggleCommand(robot, ms)`: strafes left/right (robot-centric manual drive, `JIGGLE_POWER` 0.3, 200 ms strokes, starting with a half stroke so it stays centred; heading not held) to shake balls into the intake; ends after `ms` and stops the drive. Auto runs it in a `ParallelDeadlineGroup` with `intake.intakeUntilFullCommand(timeoutMs)` as the deadline, so it stops as soon as the intake is full.
  - `Commands/PruneCommand(robot, power, ms)`: drives straight back at `|power|` for `ms`, then straight forward for `ms` (so it ends about where it started; total 2 x `ms`; both parameters are magnitudes, signs ignored), no strafe (robot-centric manual drive, heading not held), then stops the drive. Complements `JiggleCommand`: auto uses it to pull any pollen the flower has released into the intake (`G1A` runs `new PruneCommand(robot, 0.4, 250)` before the volley).

If no start pose has been set since the app started (`getSavedPose()` null, e.g. testing teleop without running auto) it does the same reset at init, and the init telemetry `Start pose` line says which (with the restored x, y, heading); rumble on full / empty; gamepad LED shows count. Gamepad 2 D-pad up/down adds/removes simulated balls. `Util/IntakeTestOpMode` runs the intake state machine alone (Cross shoot, Circle eject, Triangle pass, R1 = "shooter ready").
  - `VisionSubsystem`: webcam AprilTag cluster tracking. Also a yellow ball finder on the same camera: one `ColorBlobLocatorProcessor` over the whole image using `BiobuzzRobot.POLLEN_YELLOW` (the only ball color; no PredominantColorProcessor). Both finders are OFF after `init()` (they cost camera CPU, which slows the loop); opmodes turn on what they need with `enableAprilTags(bool)` / `enableBallFinder(bool)`: in teleop both are behind flags, currently both false: `BALL_CHASE_ENABLED` (hold L1 to chase a ball; was for testing) and `CLUSTER_AIM_ENABLED` (hold R2 also turns toward the AprilTag cluster when seen; a possible fallback for goal aim); when a flag is on, its finder runs only while that control (L1 / R2) is held. `ColorTrackingTestOpMode` turns the ball finder on at init. `waitForTipUpCommand()` / `waitForTipDownCommand()` (for auto, each also with a `timeoutMs` overload) wait for the hive tilt `getTiltAngleDeg()` (the cluster's pitch in degrees, signed: positive as the hive tips down; all comparisons are signed) to drop below / rise above `TILT_THRESHOLD_DEG` (10); with no valid cluster the tilt is `NO_CLUSTER_TILT_DEG` (90, i.e. above the threshold), so tip-up keeps waiting and tip-down ends; neither decides until a frame has been processed with AprilTags on; both turn AprilTags on while they run and back to how they were when they end. `tiltAngle()` is the tilt as a `DoubleSupplier` for conditional commands, and `isHiveUp()` / `hiveUp()` (a `BooleanSupplier`) is true when the tilt is below `TILT_THRESHOLD_DEG` (false with no cluster), the same test tip-up waits for. `GFORCE_Auto` turns AprilTags (cluster tracking) on in `initialize()` and off in `end()` (SolversLib's `CommandOpMode` calls it however the run ends, even a stop during init); `GFORCE_Teleop` turns them off in `initialize()` to make sure. Calibration uses neither. While off, `hasBall()` / `hasTarget()` are false, and results count only after a new frame has been processed since enabling. Switching goes through the `Switchable` wrapper (skips processing and drawing while off), never `setProcessorEnabled(false)`: on the color locator the SDK then draws the preview with no results and crashes (NPE in `ColorBlobLocatorProcessorImpl.onDrawFrame`). `getBlobs()` returns the SDK's own list, so copy it before filtering. Settings match the `Concept: Color-Locator (Rectangle)` test program: camera 320x240 with auto exposure (`MANUAL_EXPOSURE = false`; this also applies to AprilTags, which lose range), erode 3, blur 5, default box-fit drawing, blobs between `MIN_BALL_AREA` 400 and `MAX_BALL_AREA` 6000 pixels. It picks the blob lowest in the image (largest box-fit center y = nearest); `hasBall()`, `getBallError()` -1..+1 across the image, `getBallHeadingErrorRad()` (heading error in radians, + = CCW, from the pixel x and the hand-entered `CAMERA_HFOV_DEG`, 0 if no ball), `getTargetHeadingErrorRad()` (cluster bearing in radians), `BALL_DRIVE_POWER` (0.2) for chasing. `Util/ColorTrackingTestOpMode` drives robot-centric and chases the ball while L1 is held (sticks override); telemetry shows where it is (LEFT/CENTER/RIGHT, pixel x/y, error, area), LED yellow while seen.
  - `ShooterSubsystem`: turret (motor + encoder: bare goBILDA, 28 ticks per motor rev, geared 20T:40T then 24T:176T = 14.67:1, so `TURRET_TICKS_PER_RAD` 65.4, about 1.1 ticks per degree), hood (servo) and one flywheel. It aims at the hive-Cell from Pedro odometry and leads the target to shoot on the move. Speed and hood come from `SHOT_TABLE` (distance → rpm, hood angle, flight time). Hood angle is degrees from vertical, forward positive; `hoodAngleToServo` is the only place that converts it to a servo position, using two measured points (`HOOD_ANGLE_A/B_DEG`, `HOOD_SERVO_A/B`; currently servo 0.64 = 0° (assumed), 0.96 = 25°) and limits the hood to that range. The table is currently a cubic fit (`shotcal.py --fit --degree 3`) of 10 real shots at the audience goal with the new shooter (20.6-84.2 in, taken 2026-11-19; none timed, so flight times are carried over from the old table), extrapolated to 12-96 in: rows outside the measured range are marked `// extrapolated`, below about 17 in the hood is clamped at 0 deg and from about 84 in at its 25 deg limit (a cubic swings past its data, so the extrapolated ends are a guess); more shots are measured with `Util/ShooterCalibrationOpMode` ("Shooter Calibration"): pick a point (D-pad: distance from the goal 12-96 in in 3 in steps (`MIN_DIST`, `MAX_DIST`, `DIST_STEP`), angle off the goal's front -60..+60 deg in 15 deg steps (`MAX_ANGLE`, `ANGLE_STEP`); `AUDIENCE/FAR_GOAL_FACING_DEG` are placeholders), X drives there with Pedro (sticks cancel) and turns aiming on when it arrives; aiming at the goal starts off, R3 toggles it (twisting the right stick overrides); Circle flywheel on/off, Triangle/Cross RPM +/-50, R2/L2 hood +/-1 deg, hold R1 shoot, L1 when the ball goes in (flight time: from the ball count dropping while SHOOTING, minus `COUNT_DEBOUNCE_MS`, to the press). Shoot ONE ball at a time: the opmode keeps a snapshot of the last shot (the RPM and hood it was shot with, the flywheel speed measured as it left, battery volts, flight time, pose and distance), and that snapshot is what gets saved, not the current dials (saving with no shot, or the same shot twice, is refused). Shots can be calibrated from anywhere: the preset points and Square drive-to are only a convenience, and each row records where the shot was taken (x, y, dist); `set_dist` and `set_angle` are left blank in new rows. Every save appends a row; nothing is replaced or filtered, and repeats are all kept. Share saves it as a best shot to `/sdcard/FIRST/shooter_cal.csv` on the hub (kind `best`; these build `SHOT_TABLE`), L3 (left stick press) saves it as a compensation shot (kind `comp`, for working out hood compensation for a sagging flywheel, never used for `SHOT_TABLE`; `shotcal.py` and `plotcal.py` skip them), Options twice within 2 s undoes this session's last save (older rows: edit `tools/shooter_cal.csv` and `--push`). CSV columns: `time,goal,set_dist,set_angle,x,y,heading_deg,dist,rpm,hood_deg,tof_s,tof_n,kind,rpm_meas,volts` (older 12-column rows have no kind and count as best); every change first copies the file to `shooter_cal.csv.bak-<yyyyMMdd-HHmmss>` (the newest 5 are kept); telemetry lists the best shots saved within 3 in of the robot's current distance. Bad data can also be removed on the PC: edit `tools/shooter_cal.csv` and `python tools/shotcal.py --push` (copies it back to the hub, the hub's old file to `.bak`), otherwise the next pull brings the lines back. Then `python tools/shotcal.py` (`--csv FILE`, `--dry-run`) pulls the CSV over ADB into `tools/shooter_cal.csv` (commit it), uses every best row (no de-duplication), groups them by measured distance into 3 in bins (`BIN_IN`) and averages each bin into one table row (untimed flight times from a line fit), shows the spread within each bin, reads columns by position (an old 12-column header doesn't matter), and rewrites `SHOT_TABLE` between the `// BEGIN/END GENERATED SHOT_TABLE` markers (don't hand-edit inside them). `--fit` (with `--degree 1` default, `2` or `3`) instead fits RPM, hood and flight time to distance by least squares and writes a row every 3 in from 12 to 96 in, clamping hood and RPM to the hardware limits and marking extrapolated rows; prefer degree 1 until there is data across the range (a curve extrapolates badly). `setRequireChassisAim(true)` (teleop and auto; auto volleys use `robot.aimAndShootCommand()`: `aimAtGoalCommand()` turns in place with Pedro's `hold()` to `heading + getAimError()` at the current x/y (re-held when the aim moves `AIM_RETARGET_RAD`; done when `isAimed()` and the turn rate is under `AIM_SETTLED_TURN_RATE`; with `TURRET_ENABLED` the aim error is 0 unless the turret is at a limit, so it just holds and finishes once settled), at most `AIM_TIMEOUT_MS`, then `intake.shootAllCommand()` with an overall `VOLLEY_MAX_MS` (2.5 s from the shoot request; `VOLLEY_TIMEOUT_MS` only starts at the first feed, so without it a shooter that never gets ready would stall auto); Pedro keeps holding that pose until the next path) adds `isAimed()` (chassis within `AIM_TOLERANCE_RAD`) to `isReady()` while tracking, only while `TURRET_ENABLED` is false; `isAtSpeed()` is the flywheel part. `blockedReason()` lists every failing `isReady()` check with its numbers (speed actual/target and error, turret error or unreachable aim, chassis aim error, IDLE, no target), null when ready; keep it in step with `isReady()`. While fire is held and the shooter isn't ready, shooter telemetry adds a `BLOCKED` line with it (teleop and calibration); teleop also shows `BLOCKED no balls` when ready with an empty intake. Flywheel speed control: one target (`targetRPM`, from the shot table; teleop tracks from init so it never idles), held by our own loop in `periodic()` with the motor in `RUN_WITHOUT_ENCODER` (the hub's velocity PIDF is no longer used; since 2026-11-17, because it had no battery compensation, its P was far too weak, and every boost changed the motor mode and reset its integrator, so the flywheel sagged ~880 RPM for seconds after each volley): power = (`FLYWHEEL_KS` + `FLYWHEEL_KV` x commandRPM) / battery volts (voltage-compensated feedforward: KS and KV are in volts, so dividing by the battery gives power) + `FLYWHEEL_KP` x error + an integral (`FLYWHEEL_KI`, clamped to `FLYWHEEL_I_MAX_POWER`, builds only within `FLYWHEEL_I_ZONE_RPM` and is frozen while ramping or boosting, never reset by boost), clipped to 0..1. Battery volts are read every `VOLTS_PERIOD_S` (0.25 s; a hub call, not in the bulk read; `getBatteryVolts()`). KS 2.45 V and KV come from a 1000-6000 RPM sweep on a fresh battery (2026-11-17, within 0.3 V of a straight line; KV 0.00149 at ratio 1.5; with the 4/3 pulleys the load dropped and KV is 0.00116 from a 21:48 teleop log at ~4000 RPM, KS unchecked until a new sweep); repeat the sweep on a drained battery to check the voltage compensation; `shotlog.py` prints a `FLYWHEEL_KS` / `FLYWHEEL_KV` fit from the steady stretches of each log (volts applied = power x battery vs speed, skipping full-power rows) to paste in. `setPower` is only re-sent when it changes by `POWER_MIN_STEP`. Telemetry's Flywheel line shows `pwr`. While boost is allowed (`setBoostSupplier`, wired in `BiobuzzRobot` to shoot held or the intake full, so it is already at speed when the driver fires; `setShootingSupplier` (shoot held) only shows the `BLOCKED` line) and the speed is more than `BOOST_ENTER_RPM` (100; the speed reading moves in ~64 RPM steps, so it must be more than one step or it chatters) below target, the power is `BOOST_POWER` (1.0) until the speed is at or above the target (`BOOST_EXIT_RPM` 0); no mode change. `isBoosting()` and the telemetry line show it. `BOOST_ENABLED` (true; false = loop only) switches boost off. Spin-up ramp (the flywheel is heavy and the belt slips if asked for full speed from a standstill): when the target is set while the flywheel is below `RAMP_START_RPM` (300), the speed asked of the loop (`commandRPM`) rises at `RAMP_RPM_PER_S` (4000 since 2026-11-21; was 2000; 3000 was tried once and set back) but never more than `RAMP_MAX_LEAD_RPM` (1000) above the measured speed, until it reaches the target; boost and the integral are off while ramping; once running, speed changes are not ramped. `isRamping()`; telemetry shows `RAMP (asking N)`. `isAtSpeed()` still compares with the target, so nothing is fed until the ramp is done. `getGoal()` is the goal being aimed at (always the one on the robot's side); `getActualRPM()` / `getMeasuredRPM()` are the flywheel speed read this loop (the commanded speed while `SHOOTER_SIMULATED`). The shooter motor is a goBILDA 5203 (`MOTOR_TICKS_PER_REV` 28, `MOTOR_FREE_RPM` 5500) driving the flywheel through a belt, a speed increaser: `FLYWHEEL_GEAR_RATIO` = flywheel revs per motor rev (4/3, 1:1.333). Every RPM in the code, telemetry, `SHOT_TABLE` and the calibration CSV is FLYWHEEL RPM; only `rpmToTicksPerSec()` (flywheel RPM -> motor ticks/s for `setVelocity`), `ticksPerSecToRpm()` (`getVelocity` -> flywheel RPM), `flywheelToMotorRpm()` / `motorToFlywheelRpm()` know about the motor. `FLYWHEEL_MAX_RPM` = motor free speed x ratio (the calibration RPM limit). Data recorded before the ratio is set was taken as 1:1, so if the ratio changes, scale the old RPMs (CSV and table) by it. History: the belt was really 48:29 (1.655) until 2026-11-17, though the code said 1.0 (to 2026-11-15) and then 1.5. The 7 shots of 2026-11-14 (recorded at 1.0) were first scaled by 1.5 (2026-11-16), then corrected on 2026-11-17 to x 48/29 of the recorded values (`rpm` and `rpm_meas`, local CSV and hub; the hub's two 11-17 rows, taken while the flywheel sagged, were dropped) and `SHOT_TABLE` rebuilt (`--fit`). Turret homing: there is no home sensor, so `homeTurret()` zeroes the encoder where the turret is, and it must be centered by hand first (zero = the middle of its travel, pointing straight backwards). `GFORCE_Auto` homes at every init (its init screen says so); other opmodes home in `init()` only if nothing has since the app started (static `turretHomed`), so teleop keeps the count auto left (the hub keeps encoder counts between opmodes). Turret range (`TURRET_ENABLED`): the cabling limits it to `TURRET_MIN/MAX_RAD` (+-190 deg (narrowed for testing; was +-230)). The target is continuous (`updateTurretTarget()`: the copy of the aim angle nearest the last target, so it doesn't wrap at +-180). Not shooting (shoot not held, `setShootingSupplier`): kept within +-180, and once the aim is more than `TURRET_FLIP_MARGIN_RAD` (10 deg; 180 + margin must fit inside the limits) past 180 it flips (a 360 to the same aim within +-180; telemetry `FLIP`). Shooting: never flips; at a soft limit the target is clamped and the rest (`turretOverflowRad`) is what `getAimError()` returns, so teleop point-at-goal / auto `aimAtGoalCommand()` / Shooter Calibration turn the chassis by it (telemetry `LIMIT chassis +N`; `isReady()` waits until the turret can reach). With the turret enabled the Turret line shows `want` (the angle before the limits) instead of `aim`. At turret 0 the shooter faces straight backwards (`TURRET_ZERO_RAD` = 180 deg, since 2026-11-17): `getAimError()` (chassis aim), the turret angle and its limits, and Shooter Calibration's drive-to heading all allow for it, so point-at-goal turns the robot's back to the goal. Three independent flags: `TURRET_ENABLED` true = the turret aims the shooter and the robot heading is only changed by the driver, except while shooting with the turret at a soft limit (`getAimError()` is then the rest of the turn, otherwise 0; teleop point-at-goal only turns the chassis then, and keeps the heading lock otherwise; `isReady()` checks the turret is within `TURRET_TOLERANCE_RAD` and can reach the aim); false = the turret is held at 0 and the chassis aims instead (teleop point-at-goal, `getAimError()`; `isReady()` checks the heading if `setRequireChassisAim`). `SHOOTER_SIMULATED`: the flywheel motor is still commanded, but its speed is read back as the commanded speed. `TURRET_SIMULATED`: the turret motor and hood servo are still commanded, but the turret angle is read back as the commanded angle. All three devices (`turret`, `shooter`, `hood`) must be in the config either way. Now: `TURRET_ENABLED = true` (turret testing: the turret aims, the chassis only turns at a soft limit), `SHOOTER_SIMULATED = false`, `TURRET_SIMULATED = false`; telemetry warns while either is simulated and the Turret line says who aims. - `Util/TurretTuneOpMode` ("Turret Tune", `@Utility`): tunes the turret loop; the robot runs the tests and the fitting, and Panels (`com.bylazar:fullpanels`, http://192.168.43.1:8001; first use of Panels in the code) is the PC view: live graph (target / actual / power / omega / volts), results, and `TurretTuneConfig` (`@Configurable`, non-final static fields: `KP KI KD KS KV` live gains, `STEP_DEG` 5, `WINDOW_DEG` 15, `CHECK_POWER`, `BANDWIDTH_RAD_S`, `DAMPING`), pushed to the shooter every loop. ## Autonomous paths: `.turt` -> Java
- Draw paths in Turtle Tracer and save the `.turt` files in `/turt_files`. Commit every `.turt` file.
- Files are grouped by the text before the last underscore (`G1A_start.turt`, `G1A_2.turt` -> group `G1A`). Each group needs exactly one `_start` file; its start position becomes `getStartPose()`.
- `tools/turt2java.py` writes `paths/Path_<Group>.java` for each group: `path_start()`, then `path_<suffix>()` for the rest in natural order (2, 3, ... 10), each returning a `FollowPathCommand` (actually a `paths/NamedFollowPathCommand`, which also tells `BiobuzzRobot.setCurrentPath` the `.turt` name and each line's end-point name, so auto telemetry shows the path and line). A new file is copied from the template `paths/Path_GroupName.java` (its `autoCommand()` runs every path in order). After that, everything above the "Do not change anything above this line" banner is yours to edit (e.g. `autoCommand()`); everything below is regenerated on every run. It also regenerates `paths/AutoRoutine.java` (enum with one entry per path FAMILY; do not edit). A group named `<Family>_NT` (e.g. `Fred_NT`) is the no-turret (robot-only goal pointing) version of family `Fred`: the menu lists `Fred` once, and `command(robot, noTurret)` runs `Path_Fred_NT` when No turret is TRUE, else `Path_Fred`. If only one version exists it runs either way (the menu says so). `.turt` file names are `Fred_<n>` / `Fred_NT_<n>`. Path families are named by start area, which flips between red and blue: `G` = Garden, `L` = Loading Zone (e.g. `G1A_NT`, `L1A_NT`), not Near/Far.
- A line with a speed cap in Turtle Tracer (`maxSpeed` / `chainMaxSpeed` in the `.turt`, in/s; lowest wins) gets `.with(maxVelocity(n))`, a generated helper returning the follower's own `Foresight.config.maxVelocityConstraint.at(n)` (not `Constants.foresightConfig()`, which is a fresh copy). The cap applies only while that line runs.
- A bad group (e.g. no `_start` file) or `.turt` file prints an error and leaves every path file untouched.
- Run it manually with `python tools/turt2java.py`. The Gradle task `:TeamCode:generatePaths` does the same before every build (hooked to `preBuild`); a bad group fails the build. If Python isn't installed, the task warns and skips.
- `GFORCE_Auto` schedules `autoCommand()` on the first loop after START.
- Set the odometry start with `robot.setStartPose(pose)` (every `autoCommand()`, Touchpad, Shooter Calibration), never `drive.setPose()` directly: it also saves the pose and makes `update()` keep saving it, which is what teleop restores. The saved pose survives opmode changes (the OctoQuad pose does not) and is lost when the Robot Controller app restarts (power cycle or a new deploy), so after deploying between auto and teleop, teleop resets the pose to the auto start. An opmode that never calls `setStartPose()` (e.g. ColorTracking) doesn't overwrite it.

## Conventions
- Gamepads are PS4 (DualShock) style: name buttons by their PS4 names everywhere (code, comments, telemetry, docs): Cross, Circle, Square, Triangle, Share, Options, PS, Touchpad, L1/R1 (bumpers), L2/R2 (triggers), L3/R3 (stick presses), D-pad. In code use `GamepadKeys.Button.CROSS/CIRCLE/SQUARE/TRIANGLE/SHARE/OPTIONS` and `gamepad1.cross/circle/square/triangle/share/options` (same buttons as A/B/X/Y/BACK/START). Bumpers, triggers and stick presses have no PS-named field, so the code keeps `LEFT_BUMPER`, `right_trigger`, `RIGHT_STICK_BUTTON` etc. with an L1/R2/R3-style comment.
- **Manual driving must behave like Pedro's autonomous driving.** Teleop and test opmodes turn through the same Foresight controllers as paths (`BiobuzzRobot.turnForError` / `turnToHeading`, which mirror `Foresight.headingFeedback()`: `headingFeedback` plus `headingStaticFF`), so a tuning change in `pedro/Constants.java` shows up in both auto and teleop. Keep it that way: don't add separate gains or deadbands for manual driving, and where manual driving must differ from Pedro, say so in a comment. (`turnForError` has no static-feedforward deadband, like Foresight; if buzzing at the target ever proves one necessary, it has to apply to paths too.) When proposing a change to the Pedro constants or these helpers, remind the user that it affects both auto and teleop driving.
- Keep opmodes thin; put mechanism logic in subsystems with command factories.
- **SolversLib `withTimeout()` skips `end()`.** In SolversLib 0.3.6, `withTimeout()` is a `ParallelRaceGroup`, whose `end()` only ends commands that have NOT finished; a command that finishes by itself inside it never gets `end()`. So any cleanup a command does in `end()` (releasing shoot, turning a camera processor off) must also be done in its `isFinished()` when it returns true, as `IntakeSubsystem.shootAllCommand()` and `VisionSubsystem`'s tip-up / tip-down waits do (found 2026-11-21: auto left shoot held after every volley, so the intake never ran).
- **Loop time / bulk reads.** `BiobuzzRobot.initialize()` puts every hub in MANUAL bulk caching (`CommandScheduler.setBulkReading`); the scheduler clears the cache at the end of each `run()`. So read hub hardware (encoders, velocities, digital inputs) only inside a subsystem's `periodic()`, once per loop, and keep the value in a field (e.g. `ShooterSubsystem.actualTurretRad`); a read after `super.run()` triggers an extra bulk read. Code that reads outside the scheduler (init_loop) must call `robot.clearBulkCache()` first or it sees frozen values.
- **Telemetry** is kept short so it fits the Driver Station screen without scrolling. Teleop: Balls (count, pattern, mode, flower UP/DN), Shooter (mode, alliance, goal, distance, status), Flywheel (target / actual rpm, hood, RAMP/BOOST), Turret (target / actual, aim), Goals (distance to each, field heading to the aim point), Cycle (loop time and its average), Pose, Vel. Auto: the same subsystem lines, then Pose and Follower (mode, busy, and `robot.pathStatus()`: current path > line (n/total), e.g. `G1A_NT_2 > point2 (2/2)`; the last path stays shown while holding its end). Shooter Calibration: the same subsystem lines, then Cycle, Pose, Log as in teleop, then only its own: Cal (set rpm, shown even while the flywheel is off; OFF / AT SPEED / spinning up; aim on/off), Point, Last shot (and `at`), Saved, Near (best shots saved near this distance); don't repeat what the subsystem lines already show. Vision lines (Tags, Ball) show only while that finder is on; the intake powers line only with `intake.setShowPowers(true)` (`IntakeTestOpMode`). Merge related values onto one line rather than adding lines.
- Hardware names used so far: `front_left_drive`, `front_right_drive`, `back_left_drive`, `back_right_drive`, `octoquad`, `intake`, `transfer`, `gate`, `flower`, `slot1`, `slot2`, `slot3`, `slot4`, `turret`, `shooter`, `hood`, `Webcam 1`.

## Setting up a new PC
If the user says they are on a new machine, offer to run through this checklist (check each item with a command, don't assume):
1. `git clone` the repo and check out `BIOBUZZ-Master`. Confirm `git config user.name` / `user.email` are set.
2. Android Studio installed, with its bundled JDK (17+). Command-line `java -version` may still say 8; that's OK for Android Studio builds.
3. Python 3 on the PATH (`python --version`). Needed by the `generatePaths` Gradle task; without it `AutoPaths.java` can silently go stale. Verify with `python tools/turt2java.py` (should list every `turt_files/*.turt` file and leave `git status` clean).
4. Do a build in Android Studio and confirm it succeeds and `git status` stays clean.
5. Claude conversation history and memory are local to the old PC and are not in the repo; this file is the continuity.
